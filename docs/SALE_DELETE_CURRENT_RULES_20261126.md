# SaleDelete: primer checkpoint de reglas, no activación

`scripts/lib/sale-delete-current-rules.cjs` es puro, sin IO ni flags: `prepare(rawBytes, {expectedBaselineSha256})`. Sólo admite baseline exacto SHA256 `5a5f7b34de6cbba2ae54517029de956b6be605e21143fe4a86c131255052e48f`; Root debe volver a contrastarlo con las reglas efectivas antes de cualquier aplicación. No se incluye el respaldo privado en Git.

Tres etapas fijas: History write-side existente; Financial write-side existente; precondición AND sobre cada grant existente de Activity7 y H3. Activity7: agenda, ordenes, listas_materiales, remitos, equipos, tickets, ordenesTrabajo. H3: reclamos, equipos, tickets. El cierre conserva la autoridad original como AND independiente: durante lease requiere fence nativo de usuario o servidor con recibo y liberación atómica; idle conserva la política previa. Contempla comodines de `sisventas`; rechaza padres/raíz con autoridad no cerrada. Las reglas nativas anteriores siguen vigentes: este wrapper no concede acceso si la rama original lo deniega.

No usa `commercial-write-cut-rules` (incluye SaleReturn/OTDelete), ni `operational-write-fence.prepare` entero (agrega rama genérica server y extiende inventario/resúmenes fuera del alcance). Reutiliza sus primitivas nativas de fence como restricción, sin grant nuevo sobre fuentes. History/Financial incorporan únicamente sus raíces técnicas cerradas a clientes. CC, Pages, PaymentMembership, Guard, recibos y configuración se preservan exactamente.

Pruebas iniciales: 2 PASS de composición exacta, preservación de originales/validadores/read, bytes baseline intactos y rechazo de baseline/opciones no autorizados. **No equivalen a prueba nativa, cierre de escritores ni activación**.

Siguiente prueba acotada obligatoria con JWT/claims emitidos por Command + Guard + RESTStore actuales, sin tokens positivos manuales ni fallback Admin: candidato compilable sobre 5a; H/Financial metadata preparados comparados con CC/Pages/Payment ya instalados; SaleDelete positivo permitido, recibo/replay un efecto, proyecciones íntegras; ausencia Activity y financiero demostrada; SDK idle y user/server fenced autorizados según política original; SDK durante lease, actor/rol/revisión/reset, fence/recibo adulterado, H/Fin writer ausente y phantom tras última lectura rechazados. Cubrir padres/comodines y H3 sin permitir grants heredados de bypass. Candidatos cambiantes o fixtures financieros en RAM declarados no acreditan esa prueba.

El montaje propuesto por Root agrega sólo opt-in `Guard.saleDeleteActivity` para sus siete `affects`; getter readonly y `store.saleDeleteActivityFenceReady` derivado del montaje. No sustituye cierre Rules ni revisión de escritores. Frontend H3 necesita routing coordinado antes de habilitar H. No nuevo índice de relaciones: el comando conserva fullscan/replan sólo en la eliminación destructiva. OrderDelete/OTDelete no se habilitan por este checkpoint. No datos, Rules ni configuración remotos modificados.

Follow-up: cuarta etapa `sale-delete-current-actor-all-grants` agrega exclusivamente un AND condicionado a `auth.token.svFinancialAction === 'ventas.eliminar'` en todos los grants existentes, incluidos padres/comodines/recibo. Exige usuario admin activo, rol y revisión fijados por el emisor, módulo venta, eliminar no false, reset y lease user/UID/fence/op/digest/expiry. No nuevo claim, grant ni namespace. Los otros actions conservan la semántica previa; la única envoltura nueva se remueve exactamente para comprobar preservación de CC/Pages/Payment/metadata. Root debe emitir esa acción literal desde el comando genuino antes de probar el cierre nativo. Cinco pruebas focales de composición/predicados aprobadas; no es todavía una prueba positiva de negocio ni JWT emitido por Command.
