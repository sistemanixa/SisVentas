# Eliminación administrativa existente: referencia física OFF

Adaptación de `purchase-order-delete`, no una operación nueva de archivo. Conserva la API actual y su recibo de reintento. `referenceEnabled` es una inyección interna, false por defecto; cuando se solicita, requiere resolver autoritativo y verificador de la cohorte común, nunca un booleano de cliente como autorización. No se instala una ruta ni se cambia la UI.

El servidor sigue exigiendo exclusivamente administrador, aun si una configuración de administrativo contiene `ordenes.eliminar:true`. El flujo nuevo resuelve los tres identificadores antes de cargar el inventario y usa la clave física; la identidad guardada del producto/orden queda intacta. El modelo usa producto canónico sólo al reconciliar el renglón de Venta.

Las fuentes vinculadas requieren cuentas, historial y cobertura financiera preparados. Venta/lista y todas las otras órdenes referenciadas se leen internamente y se comprueban de nuevo. El plan elimina la orden seleccionada y sólo sus referencias, conservando las demás órdenes. Los resultados completos de referencia —incluidos rangos— forman parte de la comparación privada antes de confirmar; la dependencia financiera/configuraciones también. La admisión se vuelve a verificar después del plan final y Auth/permisos al terminar.

Evidencia ficticia: 30/30 pruebas preexistentes de modelo/comando; 8/8 nuevas de referencia (P→J, conservación de otras órdenes/pagos/comisiones/precios precisos, administrativo con override rechazado, cambios de otra orden/rango/cohorte/rol rechazados y modelo puro sin mutación y protección de custodia OT por asignación). 38/38 PASS focales finales. Combinación de este bloque con recepción/source-store/imagen: 60/60 PASS. La imagen se revisó con el COPY real, sin build ni red.

Límites: los nuevos casos inyectan un resolver de contrato, no demuestran la integración con el core E ni su grant RTDB. Referencias históricas ambiguas se rechazan. Se conserva el rechazo de reversión de costo recibido cuando hay otras órdenes, porque aún falta atribuir el costo por operación; no se borran otras órdenes ni se reescriben costos para sortearlo. Compra conjunta y custodia/OT con el core E necesitan validación específica antes de activar. El grant atómico posterior a la última lectura de cohorte requiere revisión/reglas B. No se activa el corte SDK ni se anuncia cierre de toda Compras.
